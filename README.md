# Проверка документов на соответствие справочнику терминов
Автор: Екатерина Фатеева / подготовлено с использованием Claude Code

Прототип ИИ-модуля для работы с корпоративным справочником бизнес-терминов. Он решает две задачи:

1. **Аудит справочника** — находит в самом справочнике пустые, слишком короткие и круговые определения, ошибки оформления и дубли терминов.
2. **Проверка документа** — находит в служебной записке неутверждённые формулировки и предлагает вместо них утверждённый термин из справочника.

Проверка документа идёт в три уровня: правило по известным неправильным вариантам, поиск по смыслу с помощью эмбеддингов и (по желанию) проверка языковой моделью с опорой на статьи справочника (RAG). Языковая модель работает локально через Ollama, поэтому документы не отправляются во внешний сервис.

Качество измерено на трёх размеченных документах метриками precision, recall и F1: на первом подбирается **порог**, второй служит отложенной проверкой, третий использован один раз для итоговой оценки.

## Справка

**Порог близости.** Модель эмбеддингов превращает каждый фрагмент текста и каждый термин справочника в вектор и считает между ними косинусную близость — число от −1 до 1: чем оно больше, тем ближе фрагмент к термину по смыслу. Порог — это минимальная близость, начиная с которой фрагмент считается возможной ошибкой. 

При низком пороге программа находит больше ошибок, но чаще ругается на правильный текст; при высоком реже ошибается, но пропускает ошибки, написанные своими словами. 

**Центрирование векторов.** Все финансовые термины похожи друг на друга, поэтому без обработки близость почти любых двух фраз высокая. Из всех векторов вычитается средний вектор справочника (общиай финансовый контекст), и остаётся только то, чем термины отличаются друг от друга. 

## Данные

| Файл | Содержание |
|---|---|
| `data/glossary.csv` | Справочник: 38 финансовых и корпоративных терминов. Столбцы `id` - порядковый номер термина, `term` - сам термин, `definition` - его определение, `variants` - известные неточные/разговорные (далее - неутвержденные) варианты термина через `;`. |
| `data/sample_doc.txt` + `data/test_labels.csv` | Служебная записка с 10 размеченными ошибками. На ней подбирается порог. |
| `data/holdout_doc.txt` + `data/holdout_labels.csv` | Протокол совещания с 8 ошибками. Отложенная проверка: на нём проверяется выбранный порог. |
| `data/final_doc.txt` + `data/final_labels.csv` | Пояснительная записка к бюджету с 8 ошибками. Еще раз проверяем выбранный порог модели. |

В справочник специально заложены проблемы: одно название в разном написании («Счёт-фактура» / «счет-фактура»), разные названия одного понятия («Дебиторская задолженность» / «Задолженность покупателей», «KPI» / «Ключевой показатель эффективности»), короткое и круговое определение (EBITDA, KPI), пустое определение (Тендер), название с маленькой буквы.

Ошибки в документах двух типов: «вариант» — выражение записано в справочнике как неправильный вариант термина; «смысл» — выражения в справочнике нет, понятие названо своими словами.

## Как все работает

### Аудит справочника — `glossary_check.py`

- **Правила качества**: пустое определение, определение короче 5 слов, круговое определение (слова термина в начальной форме стоят подряд в его определении), название с маленькой буквы.
- **Дубли (по названию)**: названия приводятся к начальной форме и сравниваются по доле совпадающих символов. Выявляются термины, по ошибке занесенные в справочник несколько раз.
- **Дубли (по смыслу)** — это разные названия одного и того же понятия, например "KPI" и "Ключевой показатель эффективности". По буквам они не совпадают, поэтому их ищут по смыслу. Для каждой пары терминов считается косинусная близость их векторов. Пары с близостью от 0.35 и выше выводятся как возможные дубли. Это кандидаты, а не окончательный ответ: модель не отличает одно и то же понятие от двух близких понятий, поэтому решение о том, дубль ли это, принимает эксперт.

### Проверка документа — `document_check.py`

Текст делится на предложения, каждое проверяется в четыре шага:

1. **Правильные термины** справочника находятся по начальным формам слов и исключаются из дальнейшей проверки.
2. **Уровень 1, поиск по списку вариантов.** Находятся неутвержденные варианты термина из столбца `variants` и исключаются из дальнейшей проверки.
3. **Уровень 2, эмбеддинги.** Из оставшихся слов составляются фрагменты по 1–4 слова. Каждый фрагмент сравнивается по смыслу с терминами и их вариантами справочника. Для этого используется готовая предобученная модель [`intfloat/multilingual-e5-base`](https://huggingface.co/intfloat/multilingual-e5-base) (Wang et. al, 2024): в проекте она не дообучалась, а применяется как есть. 

Модель сравнивает каждый фрагмент со всеми терминами справочника и находит самый похожий. Программа считает фрагмент ошибкой и предлагает заменить его на этот термин, если:
- фрагмент достаточно похож на термин: близость не ниже 0.55 для фрагмента из нескольких слов и не ниже 0.65 для одного;
- фрагмент не является самим термином или его куском (например, слово "капитала" из "Средневзвешенной стоимости капитала" ошибкой не считается).

4. **Одна ошибка - одно замечание.** Фразу «среднюю цену капитала» программа находит и целиком, и кусками ("цену капитала", "капитала"). В итог попадает только одна находка - та, что больше всего похожа на термин.

### Уровень 3: языковая модель — `llm_check.py`

1. Для каждого предложения эмбеддинги подбирают 5 самых близких терминов из справочника.
2. Языковая модель (в проекте используется `qwen2.5:7b`) получает эти термины, предложение, так же для нее задается строгое определение ошибки и два примера использования термина (с ошибкой и без). Модель отвечает на вопрос: есть ли в предложении ошибки и на какие термины их заменить. Ответ приходит в заданном формате, чтобы программа могла прочитать его автоматически: список найденных ошибок, где для каждой указаны слова из предложения и утверждённый термин, которым их нужно заменить. 
3. **Проверка ответа модели.** Языковая модель иногда ошибается или выдумывает, поэтому программа отбрасывает находку, если:

- указанных моделью слов на самом деле нет в предложении;
- предложенного термина нет среди пяти статей справочника, которые модели показали;
- найденные слова - это и есть правильный термин или его часть;
- это место в предложении уже отмечено как ошибка на уровне 1 или 2.

Остальные находки попадают в результат как ошибки, найденные языковой моделью.

### Оценка качества — `evaluate.py`

Для каждого документа заранее вручную составлен список всех спрятанных в нём ошибок с правильными терминами — разметка (файлы `*_labels.csv`). `evaluate.py` сравнивает найденные программой ошибки с этим списком. Находка считается верной, если программа указала на то же место в тексте, что и в разметке, и предложила тот же правильный термин. По итогам сравнения считаются precision (какая доля находок программы верная), recall (какую долю ошибок из разметки программа нашла) и F1 (общая оценка, F1 = 2 · Precision · Recall / (Precision + Recall)). Чтобы подобрать порог близости, проверка повторяется с порогами от 0.50 до 0.95 и выбирается порог с лучшим F1.

### Интерфейс — `app.py`

Для наглядности был подготовлен веб-интерфейс проекта на Streamlit: вкладка проверки документа с подсветкой ошибок и вкладка аудита справочника.

## Результаты

### Аудит справочника

Правила качества нашли все заложенные проблемы: EBITDA (короткое и круговое определение), KPI (короткое), «счет-фактура» (маленькая буква), Тендер (нет определения).

Из 703 пар терминов кандидатами в дубли выбраны 9. Все три настоящих дубля среди них: «Счёт-фактура» / «счет-фактура» (по названию, доля совпавших символов - 1.00), «KPI» / «Ключевой показатель эффективности» (по смыслу, косинусная близость - 0.36), «Дебиторская задолженность» / «Задолженность покупателей» (по смыслу, косинусная близость - 0.35). Остальные кандидаты — смежные понятия, например «Дебиторская» / «Кредиторская задолженность» (косинусная близость - 0.61). Дубли по названию определяются надёжно, а по смыслу эмбеддинги не отличают «то же понятие» от «очень близкого», поэтому это список кандидатов для эксперта.

### Выводы и ограничения

- **Поиск по списку вариантов** надёжен: находит все известные варианты без ложных замечаний, но это только то, что заранее записано в справочник.
- **Эмбеддинги** хорошо подбирают нужный термин, но по одному порогу плохо решают, ошибка ли это. Порог, идеальный на первой записке, на новых документах не нашёл ни одной ошибки по смыслу: новые ошибки пересказывают определение термина («выплата части прибыли акционерам» вместо «Дивиденды»), а их близость не выше, чем у обычных фраз («Отдел закупок» → «Тендер» 0.40, «конкурс среди поставщиков» → «Тендер» 0.41).
- **Языковая модель** находит ошибки-описания терминов своими словами ценой лишних замечаний. Однако такие замечания не всегда бесполезны. Например, модель предлагает заменить «накладные» на «Первичный документ»: это не строгая ошибка, но замена будет полезна, если нужно привести текст к формальному виду. Поэтому замечания модели лучше считать подсказками, а решение, исправлять текст или нет, оставлять человеку.
- Размеченных данных мало (26 ошибок в трёх документах), и все документы составлены специально для проекта. На реальных документах качество нужно перепроверить.

## Что можно улучшить

- Разделить столбец `variants` на допустимые синонимы и нежелательные варианты: сейчас ошибкой считаются и общепринятые аббревиатуры (WACC, NPV, IRR).
- Пополнять справочник из подтверждённых замечаний: формулировки, которые эксперт признал ошибкой, автоматически добавлять в `variants`.
- Подбирать порог отдельно для каждого термина и собрать больше размеченных документов.
- Попробовать модель эмбеддингов побольше (`bge-m3`, `multilingual-e5-large`) или cross-encoder для переоценки кандидатов.

## Запуск

```bash
python3 -m venv .venv
source .venv/bin/activate          # на Windows: .venv\Scripts\activate
pip install -r requirements.txt

python glossary_check.py                          # аудит справочника -> reports/
python document_check.py data/sample_doc.txt      # проверка документа -> reports/document_check.csv
python evaluate.py                                # подбор порога -> reports/threshold_metrics.csv
python evaluate.py --doc data/holdout_doc.txt --labels data/holdout_labels.csv --threshold 0.55
streamlit run app.py                              # веб-интерфейс
```

Для уровня 3 нужна [Ollama](https://ollama.com) с моделью:

```bash
ollama pull qwen2.5:7b
python llm_check.py data/holdout_doc.txt
python evaluate.py --doc data/final_doc.txt --labels data/final_labels.csv --threshold 0.55 --llm
```

При первом запуске скачивается модель эмбеддингов (около 1 ГБ).
